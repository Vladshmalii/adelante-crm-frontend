# Акції

Спецификация задачи бэкенда. Решения согласованы с заказчиком 2026-11-11 по видео Altegio
(«Акції», см. `frontend-loyalty-page.md`, раздел 1.2). Кода здесь нет — только постановка.
Опирается на `loyalty-accounts.md` (типы карт, уровни, расчёт скидки — раздел 6), `subscriptions.md`
и `certificates.md` (строки чека, на которые скидка не действует).

Не входят (см. `loyalty-backlog.md`): акции-бонусы, «знижка за умови», автоприменение по условиям
(первый визит, онлайн-запись, день рождения). Не делаем совсем: реферальная программа, даты и часы
действия, перенос акций из Altegio (5 акций заводятся вручную). Фронтенд — отдельная задача.

---

## 1. Согласованные решения

| # | Решение |
|---|---|
| 1 | **Акция** — отдельное правило скидки уровня сети: вид, значение, услуги, товары, типы карт, салоны |
| 2 | Акция действует **только для клиентов с активной картой** выбранных типов. Без карты — только личная скидка клиента |
| 3 | Карта **выдаётся автоматически** при создании клиента — типом с флагом «Видавати автоматично» (такой тип один). Нет такого типа — не выдаётся. Удалить карту вручную по-прежнему можно; удалённую повторно не выдаём |
| 4 | Существующим клиентам без карты карта выдаётся **один раз** (миграция данных). Тем, у кого карту удаляли, — не выдаётся |
| 5 | **Уровни скидок переезжают из типа карты в акции.** В типе карты остаются название, салоны, кешбэк, бонусные услуги. Существующие уровни переносятся в акции миграцией |
| 6 | Виды акций: **фіксована** (одно значение), **накопичувальна від суми** и **накопичувальна від кількості візитів** (уровни: порог → значение). Значение — **%** или **₴** |
| 7 | Скидка акции считается **только от строк, которые акция покрывает**: выбранные (или все) услуги и выбранные (или все, или никакие) товары |
| 8 | Применяется **одна скидка — наибольшая в гривнах** из кандидатов: личная скидка клиента и все подходящие акции (как сейчас) |
| 9 | Скидка ставится **автоматически**, администратор в окне оплаты может **заменить** её на другую подходящую или «Без знижки». Произвольную сумму ввести нельзя |
| 10 | Скидки акций действуют и **на товары** — если товары выбраны в акции |
| 11 | Акции включают и выключают **вручную** (`is_active`), без дат |
| 12 | Акции создаёт и меняет **суперюзер**; применяют администраторы всех салонов |

## 2. Данные (Master DB)

**`promotions`**
- `name`, `is_active`, `sort_order`, `created_at`, `updated_at`;
- `kind`: `fixed` | `by_amount` | `by_visits`;
- `value_type`: `percent` | `amount`;
- `value` — только для `fixed` (`percent` 0–100, `amount` > 0);
- `services_mode`: `all` | `selected`; `products_mode`: `none` | `all` | `selected`.

**`promotion_tiers`** — для накопительных: `(promotion_id, threshold, value, name)`; порог — сумма
«Продано» по карте (₴) для `by_amount` или число визитов по карте (целое) для `by_visits`; пороги
уникальны, хотя бы один уровень. Счётчики карты — как сейчас (`sold_total`, `visits_count`,
с даты выдачи карты).

**`promotion_services`** — `(promotion_id, salon_id, service_id)` при `services_mode = selected`;
**`promotion_products`** — `(promotion_id, salon_id, product_id)` при `products_mode = selected`.
Без FK на шард, EXISTS-проверка в шарде при сохранении — как у бонусных правил и сертификатов.

**`promotion_card_types`** — `(promotion_id, card_type_id)`, хотя бы один тип.
**`promotion_salons`** — `(promotion_id, salon_id)`, хотя бы один салон; в остальных салонах акция не применяется.

**`loyalty_card_types.auto_issue`** — bool; частичный уникальный индекс: не больше одного `true`.

**Удаляются** (после миграции, этапом contract): `loyalty_discount_levels`, `loyalty_card_types.level_basis`.

### 2.1. Миграция уровней (решение 5)
Для каждого типа карты с уровнями:
- уровни с `discount_percent > 0` → акция `«<тип карты> — %»`, вид `by_amount` / `by_visits` по
  `level_basis`, `value_type = percent`, уровни `threshold → discount_percent` (с именами);
- уровни с `discount_fixed > 0` → вторая акция `«<тип карты> — ₴»`, `value_type = amount`;
- услуги — `all`; товары — `all` (сейчас скидка карты действует на весь чек);
  типы карт — этот тип; салоны — салоны типа карты; `is_active` — как у типа.
Итог скидки для существующих клиентов не меняется: проверить тестом на тех же данных.

### 2.2. Выдача карт существующим клиентам (решение 4)
Одноразово (миграция данных или команда `salonctl`, идемпотентно): если есть тип с `auto_issue`,
выдать карту каждому активному клиенту, у которого **никогда не было** карты. Номер генерируется
как при ручной выдаче. В аудит — автор «Система».

## 3. Автовыдача карты (решение 3)

При создании клиента любым путём — из CRM (`POST /clients`, новая запись с новым клиентом),
публичная онлайн-запись, бот — в той же транзакции Master создаётся карта типа с `auto_issue`
(если такой тип есть и активен). Логику держать в одном сервисе создания клиента, а не в каждом роутере.
Номер — как при ручной выдаче; `issued_by` — автор действия (в боте и онлайн-записи — «Система»).

## 4. Расчёт скидки (меняет `loyalty-accounts.md`, раздел 6, шаг 2)

1. **База строки** — сумма строки после бонусных услуг, абонементов и без строк-сертификатов (как сейчас).
2. **Кандидаты:**
   - личная скидка клиента — % от всей базы (как сейчас);
   - каждая **подходящая акция**: активна, салон чека в `promotion_salons`, у клиента активная карта
     типа из `promotion_card_types`, карта действует в этом салоне. Для накопительной — текущий
     уровень по счётчикам карты (нет достигнутого уровня — не кандидат).
3. **Покрытые строки акции:**
   - строки услуг — при `services_mode = all` все, иначе пара (салон, услуга) из списка;
   - строки товаров — при `products_mode = all` все, `selected` — пара (салон, товар) из списка, `none` — никакие;
   - строка-абонемент (покупка) — только при `services_mode = all` (абонемент — предоплата услуг).
4. **Сумма кандидата-акции:** `percent` — % от суммы покрытых строк; `amount` — `min(значение, сумма покрытых строк)`.
5. Выбирается **наибольшая в гривнах** (при равенстве — личная, затем акция с меньшим `sort_order`).
   Скидка распределяется **только по покрытым строкам** (личная — по всем), пропорционально, как сейчас.
6. **Выбор администратора** (решение 9): в запросе оплаты и предпросмотра — `discount`:
   `{"source": "auto"}` (по умолчанию) | `{"source": "client"}` | `{"source": "promotion", "promotionId": …}` |
   `{"source": "none"}`. Выбранный кандидат должен быть в списке подходящих — иначе 422.
7. **Снимок в чеке/записи:** `discount_source` получает значение `promotion` (вместо `card_percent` /
   `card_fixed`; старые значения остаются для истории), плюс `discount_promotion_id`,
   `discount_promotion_name`. Миграция shard.

Кешбэк, «Продано» и визиты карты считаются как сейчас.

## 5. API (всё под `/api/admin/v1`, camelCase)

**Акции** — суперюзер (чтение — администратор, чтобы видеть названия в окне оплаты):
- `GET /promotions?active=`, `GET /promotions/{id}`, `POST /promotions`, `PATCH /promotions/{id}`.
- `DELETE /promotions/{id}` — только если акция ни разу не применялась в чеках (EXISTS по снимку
  `discount_promotion_id` во всех шардах); иначе 409 «Акцію вже застосовували — вимкніть її».
- Поля: `name`, `isActive`, `sortOrder`, `kind`, `valueType`, `value`, `tiers [{threshold, value, name}]`,
  `servicesMode`, `services [{salonId, serviceId}]`, `productsMode`, `products [{salonId, productId}]`,
  `cardTypeIds`, `salonIds`. В ответе + `id`, `createdAt`, `updatedAt`.
- Валидация: `value` только у `fixed`, `tiers` только у накопительных; `percent` ≤ 100; пороги
  `by_visits` — целые; пары услуг/товаров проверяются в шардах; типы карт и салоны существуют.

**Типы карт:** новое поле `autoIssue`; поля `levels` и `levelBasis` убираются из входа и выхода
(этап contract — после фронтенда, см. раздел 7).

**Оплата и предпросмотр:** в `GET /records/{id}/checkout`, `GET /finances/receipts/checkout` и в
`POST /records/{id}/payment`, `POST /finances/receipts` — параметр/поле `discount` из раздела 4, п. 6.
Кандидаты в предпросмотре: `{source, promotionId, name, valueType, value, tierName, amount, selected}`.

**Карта клиента и бот:** вместо «уровня карты» — список накопительных акций типа карты с текущим и
следующим уровнем: `{promotionId, name, tierName, value, valueType, nextThreshold}`. Бот показывает
так же (только просмотр).

## 7. Этапы (expand → migrate → contract)

1. **Expand:** таблицы акций, `auto_issue`, новые поля снимка скидки в шарде; CRUD акций.
2. **Расчёт:** кандидаты-акции, покрытые строки, выбор администратора. Уровни типа карты перестают
   участвовать в расчёте в том же коммите, где появляется миграция 2.1, — чтобы скидка не считалась дважды.
3. **Migrate:** перенос уровней в акции (2.1), выдача карт существующим клиентам (2.2), автовыдача (3).
   Расчёт переключается на акции.
4. **Contract** (после фронтенда): удалить `loyalty_discount_levels`, `level_basis`, поля `levels` /
   `levelBasis` из API типа карты.

## 8. Тесты (минимум)

- CRUD и валидация всех видов, пары чужого салона, `percent` > 100;
- акция не применяется: без карты, чужой тип карты, другой салон, выключена, уровень не достигнут;
- покрытие: только выбранные услуги, товары `none`/`all`/`selected`, строка-абонемент при `all` и `selected`;
- `amount` не больше суммы покрытых строк; распределение скидки только по покрытым строкам;
- выбор наибольшей; ручная замена на другую подходящую и на «Без знижки»; неподходящая — 422;
- миграция уровней: на тех же данных итог чека тот же, что до миграции;
- автовыдача при создании клиента всеми путями; без типа `auto_issue` — нет; разовая выдача
  не трогает клиентов с удалённой картой и идемпотентна; второй тип с `auto_issue` — 422.
