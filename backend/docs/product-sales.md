# Продажа товаров по бутылкам и по объёму

Спецификация задачи. Решения согласованы с заказчиком 2026-11-04. Кода здесь нет — только постановка.

Пересматривает `loyalty-accounts.md`, раздел 15, п. 1: товары появляются в чеке визита и списываются
со склада. Закрывает вариант Б из `task-admin-sale.md` в части строк чека и списания.

**Не входят:**

- черновик товаров в записи и добавление товара мастером;
- кнопка продажи для администратора;
- отмена чека администратором;
- списание расходников бутылками;
- ручная цена строки;
- процент мастеру с продажи;
- частичный возврат товара;
- учёт нескольких открытых бутылок;
- несколько объёмов в одной карточке.

## 1. Согласованные решения

| # | Решение |
|---|---|
| 1 | Остаток — одно число в единице карточки. Бутылка = `package_volume`, отдельного счётчика нет |
| 2 | Одновременно открыта одна бутылка, поэтому `floor(остаток / объём)` — это число закрытых бутылок |
| 3 | Разные объёмы одного товара (1 л и 0,5 л) — разные карточки |
| 4 | Товар добавляет администратор в окне оплаты, по образцу продажи сертификатов |
| 5 | Склад списывается при оплате, в одной транзакции шарда с чеком |
| 6 | Цена на разлив вводится за единицу карточки (₴/мл, ₴/л), цена бутылки — отдельно |
| 7 | Цена берётся только из карточки, вручную не меняется |
| 8 | Скидки клиента и карты действуют на товары |
| 9 | Мастер не получает процент и выручку с продажи товара |
| 10 | Отмена чека остаётся у суперюзера и возвращает товар на склад |
| 11 | Продажа без записи получает те же строки товаров. Интерфейс остаётся в «Фінансах» |
| 12 | Нужен отчёт по продажам товаров |
| 13 | Реальных данных нет: пересчёт старых цен не нужен |

## 2. Модель данных (шард)

### `products`

| Поле | Изменение |
|---|---|
| `package_price` | Новое, `Numeric(12,2)`, null. Цена бутылки |
| `sale_price` | `Numeric(12,4)`. Цена за единицу карточки: за мл, г, л, кг или шт |
| `cost_price` | `Numeric(12,4)`. Себестоимость за единицу карточки (так её уже считает стоимость склада) |

Правила карточки:

- у `unit=pcs` объёма и цены бутылки нет;
- `package_price` требует `package_volume`;
- `unit` и `package_volume` нельзя менять, если у товара есть движения: 409 «Створіть нову картку».
  Правило действует и в `PATCH`, и в импорте (`inventory.py:924` сейчас перезаписывает их без проверки).

### `stock_movements`

Новый тип `MovementType.SALE = "sale"`.

- Колонка — VARCHAR без нативного enum. В миграции `create_constraint` не задан, поэтому CHECK быть не
  должно; проверить на чистой БД.
- Ручной `POST …/movements` с типом `sale` отклоняется с 422. Сейчас `_movement_delta`
  (`inventory.py:522`) вернул бы для него положительную дельту, то есть приход.
- `record_id` заполняется у продажи в визите. `_consumables` фильтрует по `WRITE_OFF`, поэтому продажи
  не попадут во вкладку «Витрати».
- Возврат — движение `RECEIPT` с `cancels_movement_id`, как при отмене списания расходника.

### Новая таблица `receipt_product_lines`

Одна строка — один товар в одном режиме. Все значения — снимок на момент продажи.

| Поле | Тип | Значение |
|---|---|---|
| `id`, `receipt_id` | FK, индекс | |
| `product_id` | FK | Товар не удаляется физически, FK безопасен |
| `name`, `sku`, `unit` | снимок | Для чека и отчёта |
| `mode` | `package` / `volume` | Режим продажи |
| `quantity` | `Numeric(14,3)` | Как ввели: 2 бутылки или 250 мл |
| `base_quantity` | `Numeric(14,3)` | В единице карточки: 2000 или 250 |
| `unit_price` | `Numeric(12,4)` | Цена режима |
| `amount` | `Numeric(12,2)` | `unit_price × quantity`, до скидки |
| `paid_amount` | `Numeric(12,2)` | После скидки |
| `cost_amount` | `Numeric(12,2)`, null | `cost_price × base_quantity`; null, если себестоимости нет |
| `movement_id` | FK, unique | Движение `sale` |
| `created_at` | | |

### `receipts`

Новое поле `products_amount` `Numeric(12,2)`, default 0: сумма `paid_amount`. По нему отчёты отделяют
товары от услуг (раздел 5).

## 3. Правила продажи

Доступность режимов определяется данными карточки, отдельной настройки нет:

| Режим | Условие | Количество |
|---|---|---|
| `package` | Заданы `package_volume` и `package_price` | Целое ≥ 1; база = количество × объём; цена = `package_price` |
| `volume`, единица не `pcs` | Задан `sale_price` | > 0, до 3 знаков; база = количество; цена = `sale_price` |
| `volume`, `unit=pcs` | Задан `sale_price` | Целое ≥ 1; база = количество |

Товар неактивен или режим недоступен — 409. Сумма строки округляется до копеек `ROUND_HALF_UP`.

**Пример.** Карточка: `unit=ml`, объём 1000, бутылка 350 ₴, разлив 0,5 ₴/мл, остаток 2000 мл («2 шт»).

1. Продали 1 бутылку: 350 ₴, остаток 1000.
2. Продали 250 мл: 125 ₴, остаток 750.
3. Попытка продать бутылку — 409: в наличии 750 мл, нужно 1000.

**Остаток.** Одинаковые товары суммируются по всем режимам чека. Сумма базы не может превышать остаток,
в минус склад не уходит.

**Скидка.** `paid_amount = amount × (база − скидка) / база`, по той же формуле, что `service_amounts`.
Копеечный остаток округления уходит на последнюю строку товара.

**Что уже работает без изменений логики:**

- скидка — `quote()` включает строку `kind="product"` в базу;
- кешбэк — `cashback_on_products` (`loyalty.py:263`);
- сертификаты «на послуги» — не покрывают товары (`certificates.py:430`);
- уровни карты — товары входят в `sold`, как в продаже без записи.

## 4. Backend

### API

**Предпросмотр.** `GET /records/{id}/checkout` и `GET /finances/receipts/checkout` получают повторяемый
параметр `products=<productId>:<mode>:<quantity>`, до 50 штук. Ответ: `lines` с `kind="product"` и новыми
полями `productId`, `mode`, `quantity`, `unitPrice`. Нехватка остатка в предпросмотре — 409.

**Оплата.** `POST /finances/receipts` получает `products: [{productId, mode, quantity}]`, до 50 строк.
Смена цены между предпросмотром и оплатой ловится через `expectedTotal` (409).

**Чтение чека.** `ReceiptOut` получает `products: ReceiptProductLineOut[]`.

**Склад.** `ProductOut`, `ProductCreateIn` и `ProductPatchIn` получают `packagePrice`. Мастеру оно, как и
другие цены, не отдаётся.

### Оплата (`services/visits.py`, `pay_record` и `sell`)

Порядок важен: блокировки и проверка должны идти до `settle`, то есть до списания со счетов в Master DB.
Иначе нехватка товара приводила бы к лишнему сторно.

1. `lock_receipt` и блокировка записи — как сейчас.
2. Блокировка товаров `FOR UPDATE` в порядке id, проверка режимов и остатка.
3. Построение `Line(kind="product")` и `Quote`, `check_total`.
4. `settle`. В `write_shard`: чек, строки, движения `sale`, `products_amount`.

В `create_receipt`:

- доход товаров отделяется от услуг, как сертификаты: `products_amount` забирается из частей оплаты по
  порядку, такая часть пишется в операцию с категорией `sales`, остальное — в `services`
  (`visits.py:303` сейчас пишет всё в `services`);
- части способом «Сертифікат» дохода не создают, поэтому покрытая ими доля товаров в `sales` не попадает.

`record.total_amount` — только услуги: `q.total − products_amount`. Его суммируют `staff_stats`
(`staff.py:676`) и агрегаты клиента (`clients.py:88`). Сумма в карточке клиента по-прежнему не включает
товары; продажи без записи в неё не входят и сейчас.

### Продажа без записи

`products` работает так же. В `visits.sell` ветка «без `subtotal` сумма чека = сумма частей» срабатывает
только при отсутствии и сертификатов, и товаров. `subtotal` в API сохраняется для совместимости.

### Отмена чека (`finances.py:922`)

- Чек читается `FOR UPDATE`: сейчас параллельная отмена привела бы к ошибке на unique
  `cancels_movement_id`.
- Товары блокируются в порядке id, по каждой строке пишется обратное движение. Работает и для
  деактивированного товара.
- Строки в запись не возвращаются: при повторной оплате администратор выбирает их заново, как сертификаты.

### Импорт и экспорт (`inventory.py`)

- Новая колонка «Ціна упаковки» в импорте, экспорте и шаблоне.
- `LEGACY_IMPORT_COLUMNS` исключает новую колонку, иначе сдвинется старая раскладка.
- Отсутствующая колонка и пустая ячейка не стирают цену у существующего товара, как штрихкод.
- Строка, меняющая `unit` или объём товара с движениями, становится ошибкой строки.
- «Залишок» и «Мін. залишок» остаются в единице карточки.

### Миграция

Одна ревизия шарда: поля `products`, `receipts.products_amount`, таблица строк. Пересчёта данных нет.

## 5. Отчёты

**Новый `GET /reports/products`** (`dateFrom`, `dateTo`) — по неотменённым чекам за период, киевские сутки.

| Колонка | Администратор | Суперюзер |
|---|---|---|
| Товар, артикул, категория | да | да |
| Продано бутылок, продано на разлив, всего в единице карточки | да | да |
| Выручка, себестоимость, маржа | null | да |

Новая вкладка на странице «Звіти» и лист «Товари» в `/reports/export`.

**Правка существующих отчётов — обязательна.** `_staff` (`reports.py:411`) и `_services`
(`reports.py:515`) считают выручку мастера и услуг из `Receipt.amount`. С товарами в чеке визита они
завысятся, поэтому там нужно `Receipt.amount − Receipt.products_amount`. Общая выручка и средний чек не
меняются: товары в них входят.

Старые чеки с ручной суммой в отчёт не попадают: у них нет строк товаров.

## 6. Frontend

**Склад (`pages/inventory`)**

- `ProductFormModal`: «Ціна упаковки»; подписи с единицей («за мл»); `unit` и объём заблокированы при
  наличии движений; начальный и минимальный остаток для фасованного товара вводятся в бутылках.
- `MovementFormModal`: приход, списание и инвентаризация для фасованного товара вводятся как «бутылки +
  остаток в единице». API получает значение в единице карточки и не меняется.
- `movementTypeLabels` получает `sale` («Продаж»), но эта кнопка не показывается в форме движения.
- `InventoryPage`: колонка цены бутылки; маржа считается по обеим ценам, когда они заданы.
- `packageBreakdown` переносится в `shared/lib/quantity.ts`: виджеты не могут импортировать из страниц.

**Новый виджет `widgets/product-sale`**

`ProductSalePicker` по образцу `CertificateSalePicker`: поиск товара, переключатель «Бутылка / На
розлив» (только доступные режимы), количество, остаток и сумма строки. Товар без цен недоступен.

**Оплата**

- `PaymentModal` (календарь) и `ReceiptFormModal` (финансы) получают picker и передают строки в
  предпросмотр и оплату.

- `CheckoutSummary` показывает строки товаров.
- После оплаты и отмены чека инвалидируется кеш `['inventory']`.

**Прочее**

- Вкладка отчёта на `ReportsPage`, строки товаров в чеке в «Фінансах».
- Перегенерация `schema.gen.ts`.

## 7. Тесты

- Склад: режимы, запрет смены единицы и объёма, отказ в ручном `sale`, импорт со старой раскладкой, без
  колонки цены и со сменой единицы.
- Продажа: бутылка и разлив в одном чеке, нехватка при суммировании режимов, 750 мл при бутылке 1000,
  параллельная продажа последней бутылки, смена цены (409), округление.
- Деньги: скидка на товары, кешбэк с `cashback_on_products` и без, сертификат «на послуги» и «на всё»,
  оплата с бонусной услугой, разделение `services` и `sales`, откат при сбое шарда.
- Идемпотентность: повтор с `Idempotency-Key` не списывает товар второй раз.
- Отмена: возврат товара, чек с деактивированным товаром, повторная отмена.
- Отчёты: выручка мастера и услуг без товаров, общая выручка с товарами, права администратора.

## 9. Открытый вопрос

Оставлять ли в форме чека без записи ручную сумму «Продано»? В спецификации она скрыта: продажа мимо
склада снова разводит деньги и остатки. API поле сохраняет.

## 10. Найдено попутно, в задачу не входит

Проданный в чеке визита сертификат тоже входит в `Receipt.amount` и `record.total_amount`. Поэтому он
завышает выручку мастера и услуг в отчётах. Это уже существующее поведение, исправляется отдельно.
