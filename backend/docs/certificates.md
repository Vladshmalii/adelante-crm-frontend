# Подарункові сертифікати

Спецификация задачи. Решения согласованы с заказчиком 2026-10-14 по скриншоту старой CRM
(группа «Сертифікати Мережа Adelante» в каталоге услуг). Кода здесь нет — только постановка.
Опирается на `money-overview.md` (как устроены деньги) и `loyalty-accounts.md` (журнал счетов).

Не входят: онлайн-продажа (сайт записи, бот), возврат денег за сертификат, процентные сертификаты,
абонементы, фискализация (ПРРО).

---

## 1. Согласованные решения

| # | Решение |
|---|---|
| 1 | Сертификат **покупается** за деньги. Номинал всегда равен цене: купил за 150 ₴ — на сертификате 150 ₴. Процентных сертификатов и «купил за 100 — скидка 150» нет |
| 2 | Один вид сертификата — **предоплаченный остаток**. Тратится частями, остаток после визита сохраняется |
| 3 | Область применения задаётся в шаблоне: **на всё** (услуги и товары, как «1000 грн (гроші на рахунку)») или **на выбранные услуги** (как «на манікюр з покриттям 150 грн») |
| 4 | Срок задаётся в шаблоне: N дней от покупки или бессрочно. По истечении остаток сгорает. Денежные сертификаты из старой CRM — бессрочные |
| 5 | Шаблоны сертификатов создаёт **только суперюзер**, один раз на сеть. Продают и погашают администраторы всех салонов |
| 6 | После оплаты генерируется персональный код. Покупатель либо **активирует сертификат на себя**, либо забирает код и **дарит** — тогда сертификат привязывается к тому, кто первым его предъявил |
| 7 | Активированный сертификат **передать нельзя** — он навсегда у владельца |
| 8 | Сертификат действует **во всех салонах сети**, взаиморасчётов между салонами нет: выручка остаётся у салона-продавца. ⚠️ *Заказчик предупредил, что это может измениться — модель не должна мешать ограничить сертификат салоном (см. 3.1, `salon_id` продажи хранится)* |
| 9 | Услуги сертификата «на выбранные услуги» задаются **парами (салон, услуга)** для каждого салона — как в бонусных правилах лояльности |
| 10 | Выручка признаётся **один раз — при продаже**. Оплата сертификатом новую выручку не создаёт |
| 11 | На строку-сертификат при продаже **не действуют скидки** (карта, личная скидка) и **не начисляется кешбэк** |
| 12 | На часть визита, оплаченную сертификатом, кешбэк **начисляется** как на обычные деньги |
| 13 | **Возврата денег** за сертификат нет. Отменить чек покупки можно, только пока сертификатом не пользовались |

## 2. Термины

- **Шаблон** — позиция каталога «Сертифікати Мережа Adelante»: название, номинал, область, срок.
  Создаёт суперюзер. Аналог услуги в старой CRM.
- **Сертификат** — экземпляр, выпущенный при оплате: код, остаток, владелец, срок.
- **Активация** — привязка сертификата к клиенту (владельцу). Один раз.
- **Погашение** — оплата части чека сертификатом.

Жизненный цикл:

```
выпущен (код есть, владельца нет — «на предъявителя»)
   │ активация: покупатель «на себя» при продаже или предъявитель при первом погашении
   ▼
активен (владелец = клиент) ──► израсходован (остаток 0) / истёк / аннулирован
```

Погасить можно и выпущенный, и активный сертификат; погашение выпущенного активирует его на клиента чека.

## 3. Данные

### 3.1. Master DB (сертификат общий для сети, как счета)

**`certificate_templates`** — шаблоны (решение 5). Не шард-услуга: иначе суперюзеру пришлось бы
заводить один и тот же сертификат в каталоге каждого салона.
- `name`, `amount` (номинал = цена), `scope` (`any` | `services`), `valid_days` (NULL — бессрочный),
  `is_active`, `sort_order`, `created_at`.

**`certificate_template_services`** — услуги шаблона со `scope = services` (решение 9):
`(template_id, salon_id, service_id)`, без FK на шард, EXISTS-проверка при сохранении —
по образцу `loyalty_bonus_rule_services`.

**`certificates`** — выпущенные сертификаты.
- `code` — уникальный, читаемый: `ADL-XXXXX-XXXXX` из алфавита без похожих символов (без 0/O/1/I/L,
  31 символ), ≈ 49,5 бит случайности. Код — это деньги: подбор перебором должен быть невозможен.
  *Уточнено 2026-10-14: 8 символов давали ≈ 39,6 бит — меньше требуемых 40.*
- Снимок шаблона на момент покупки: `template_id`, `name`, `amount`, `scope`,
  список услуг (копия пар на момент продажи — правка шаблона не меняет проданные).
- `expires_at` (NULL — бессрочный), `status` (`issued` | `active` | `spent` | `expired` | `cancelled`).
- Продажа: `sold_salon_id`, `sold_receipt_id`, `buyer_client_id` (NULL — покупатель не в базе).
- Владелец: `owner_client_id` (NULL до активации), `activated_at`.

**Остаток — в журнале `ledger`**, как кешбэк:
- новый `AccountKind.CERTIFICATE`, у `client_accounts` появляется `certificate_id` (unique);
- `client_id` становится nullable: у неактивированного сертификата владельца нет.
  Проверка: `client_id` обязателен для `money` и `cashback`. При активации — заполняется;
- выпуск — `topup` на номинал, погашение — `payment`, отмена погашения — `reversal`,
  сгорание — `burn`, аннулирование — `adjustment` в ноль.

Так остаются общие правила журнала: блокировка счёта, уникальный ключ, сторно вместо UPDATE.

### 3.2. Shard DB салона

- **Строки чека-сертификаты** `receipt_certificate_lines`: `receipt_id`, `template_id`, `name`,
  `amount`, `certificate_id` (заполняется после выпуска). Нужны, потому что сейчас чек без записи —
  одна строка «Товари». Если до этой задачи будет сделан вариант Б из `task-admin-sale.md`
  (общая таблица строк чека), используем её с видом строки `certificate`.
- Системный способ оплаты **`certificate`** без кассы — по образцу `account` и `bonus`:
  добавить в `SYSTEM_METHOD_TYPES`, создать миграцией в каждом салоне.
- Миграция: существующие пользовательские способы с типом `certificate` (с кассой) → `other`,
  как было сделано с `bonus`.

## 4. Продажа

Где: в окне оплаты визита и в продаже без записи. Над строками визита — кнопка
«+ Сертифікат», список шаблонов группой «Сертифікати Мережа Adelante», количество (1 шт. по
умолчанию; 2 шт. — два кода).

Правила:
1. Строка-сертификат идёт в «Продано», но **не участвует** в расчёте скидки и кешбэка (решение 11):
   `checkout.py` получает вид строки `certificate`, скидка считается только от остальных строк.
2. Строку-сертификат можно оплатить **только кассовыми способами**. Счёт, кешбэк и другой
   сертификат покрывают только остальную часть чека — иначе кешбэк или долг превращаются в
   сертификат.
3. Деньги за сертификат — обычная операция `income` в кассу, категория `certificates`
   («Продаж сертифікатів»). *Решено 2026-10-14:* сумма сертификатов забирается из кассовых частей
   оплаты по порядку; кассовая часть, покрывающая и сертификат, и остальное, делится на две
   операции `income` с тем же способом и кассой. `receipt_payments` — по строке на часть.
   Сумма income = деньги, пришедшие в кассу.
4. Выпуск — в `payments.settle`, в транзакции Master, вместе со списаниями: ключ
   `cert:{salon}:{receipt}:{line}:{n}` (`line` — позиция продажи в запросе, `n` — 1..количество). Если чек в шарде упал — выпуск откатывается компенсацией,
   как списания; ночная сверка аннулирует сертификаты, чьего чека нет.
5. После оплаты окно показывает коды: «Скопіювати», «Друк» (бланк с названием, номиналом,
   сроком, кодом), «Активувати на {клієнт}» (если в чеке есть клиент) — решение 6.

## 5. Погашение

В окне оплаты — способ «Сертифікат». Кассир вводит код или выбирает из активных сертификатов
клиента (подсказка с остатками).

Проверки:
1. Статус `issued` или `active`, не истёк, остаток > 0.
2. Активный сертификат чужого клиента — отказ (решение 7). Неактивированный — активируется
   на клиента чека; без клиента в чеке погасить неактивированный нельзя (некого привязать).
3. `scope = services`: сумма ≤ сумме строк, чья пара (салон, услуга) есть в снимке сертификата;
   товары не оплачиваются.
4. Сумма ≤ остатку. В одном чеке можно несколько сертификатов (ключ на каждый).

Списание:
- в `payments.charge`, ключ `pay:{salon}:{receipt}:certificate:{certificate_id}`;
- порядок блокировок в Master: денежный счёт → кешбэк → **сертификаты (по id)** → прогресс бонусов;
- обязательно добавить в `reverse_payments` и в ночную сверку.

Выручка (решение 10): часть оплаты способом `certificate` пишется в `receipt_payments`, но
**не создаёт `FinanceOperation(income)`** — сейчас `visits.py` создаёт income на каждую часть,
это главное изменение в шарде. Отчёты «оплачено по способам» берут данные из `receipt_payments`.

Кешбэк (решение 12): часть, оплаченная сертификатом, входит в базу начисления кешбэка.

## 6. Отмена, сгорание, аннулирование

| Событие | Что происходит |
|---|---|
| Отмена чека, оплаченного сертификатом | Остаток возвращается сторно (`reversal`) через `reverse_payments`, асинхронно, как со счётом |
| Отмена чека покупки | Разрешена, только если у всех сертификатов чека не было погашений. Сертификаты → `cancelled`, остаток в ноль, income в шарде отменяется как обычно |
| Истёк срок | Ночная задача Celery beat: `burn` остатка, статус `expired`. В шарде ничего — выручка уже признана |
| Аннулирование вручную | Суперюзер, с причиной, в аудит. Остаток в ноль, `cancelled`. Деньги не возвращаются (решение 13) |

## 8. Интерфейс

1. **Настройки (суперюзер)** — раздел «Сертифікати» рядом с «Лояльністю»: список шаблонов,
   форма (название, номинал, «на все» / «на послуги», срок, для «на послуги» — выбор услуг по
   салонам, как в бонусных правилах).
2. **Окно оплаты** — «+ Сертифікат» для продажи; способ оплаты «Сертифікат» с полем кода и
   списком сертификатов клиента; после оплаты — коды, печать, активация.
3. **Карточка клиента** — блок «Сертифікати»: купленные и свои, код, остаток, срок, статус,
   история погашений.
4. **Фінанси (суперюзер)** — реестр: поиск по коду, фильтры по статусу и салону продажи,
   аннулирование.
5. **Бот** — не в этой задаче (онлайн-продажи нет); показ сертификатов владельца можно добавить
   позже по образцу баланса счёта.

## 9. Этапы

1. **Основа**: таблицы Master и шарда, миграции (expand → migrate → contract), системный способ
   `certificate`, перевод старых способов в `other`. Шаблоны и экран настроек суперюзера.
2. **Продажа**: строки-сертификаты в `checkout.py`, исключение из скидки и кешбэка, выпуск в
   `settle` с компенсацией, показ и печать кодов, активация.
3. **Погашение**: способ оплаты в окне, проверки области, списание в `charge`, без income,
   `reverse_payments`, сверка, кешбэк с погашенной части.
4. **Сопровождение**: сгорание по сроку, отмена чека покупки, реестр и аннулирование,
   блок в карточке клиента.

Каждый этап — с тестами: идемпотентность выпуска и погашения, повтор после сбоя между БД,
двойная выручка (продажа + погашение = один income), область «на послуги» в другом салоне,
отмена использованного сертификата запрещена.
