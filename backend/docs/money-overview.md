# Деньги в Adelante CRM: счета клиента, оплата, кассы

Обзор того, как устроены деньги на 2026-10-13 — для работы над сертификатами и абонементами.
Это описание текущего кода, а не новая спецификация. Подробности и согласованные решения —
в [`loyalty-accounts.md`](loyalty-accounts.md) (особенно раздел 15 «Уточнения»), отложенная
задача — [`task-admin-sale.md`](task-admin-sale.md).

Сертификаты и абонементы в спецификации лояльности **явно не входили** (решение 17). Ниже в
разделе 9 — где они могут встроиться и какие вопросы надо решить с заказчиком **до** кода.

---

## 1. Где что лежит

| Данные | БД | Почему |
|---|---|---|
| Клиент, особовий рахунок, кешбек-рахунок, журнал операций | Master DB | Общие для сети: пополнил в одном салоне — тратит в любом |
| Карты лояльности, типы карт, уровни, бонусные правила, прогресс, факты визитов | Master DB | Карта общая для сети |
| Записи, чеки, части оплаты, финансовые операции, кассы, способы оплаты | Shard DB салона | Деньги салона, у каждого салона свои кассы |
| Outbox-события | Shard DB | Пишутся в одной транзакции с чеком |

Между Master и шардом нет FK и нет общей транзакции. Целостность обеспечивают:
порядок записи (раздел 5), идемпотентные ключи, outbox + Celery и ночная сверка.

## 2. Кассы и способы оплаты (шард)

### Модели — `app/models/shard/finance.py`

- **`CashRegister`** — касса (название, локация, `is_active`). **Баланс не хранится** — считается
  по операциям.
- **`PaymentMethod`** — способ оплаты: `type`, `cash_register_id` (в какую кассу идут деньги),
  комиссия, `available_online`, `is_active`. Типы `PaymentMethodType`:
  `cash`, `card`, `online`, `certificate`, `bonus`, `tips`, `other`, `account`.
  - `certificate` — **есть в enum, но нигде не обрабатывается**: это обычный способ с кассой.
  - `account` («Особовий рахунок») и `bonus` («Кешбек») — **системные**: по одному в салоне
    (частичный unique-индекс `uq_payment_methods_system_type`), **без кассы**, не онлайн, не
    редактируются и не создаются через API (`SYSTEM_METHOD_TYPES`, `PaymentMethod.is_system`).
    Создаются шард-миграцией `92d794cd9582`, поэтому есть и в новых салонах.
- **`FinanceOperation`** — движение денег: `type` = `income` / `expense` / `transfer`,
  `status` = `completed` / `pending` / `cancelled`, `cash_register_id`,
  `target_cash_register_id` (только у перевода — касса-получатель), `payment_method_id`,
  ссылки на клиента, запись, чек, документ. `category` — снапшот названия категории расходов
  (справочник `ExpenseCategory`, строка до 255 символов).
- **`Receipt`** — чек: `amount` (итог), `subtotal` («Продано»; `null` у старых чеков),
  `discount_amount`, `discount_source`, `loyalty_card_id` (снапшот карты), `record_id`
  (нет — продажа без записи), `cash_register_id` (`null` — чек без кассы), `status`
  (`paid` / `cancelled`; `partial` есть в enum, но не используется — частичной оплаты нет).
- **`ReceiptPayment`** — части чека по способам оплаты.

### Баланс кассы — `_register_movements()` в `app/api/admin/finances.py`

Сумма по `completed`-операциям: приход `+`, расход `−`, перевод — `−` у отправителя
(`cash_register_id`) и `+` у получателя (`target_cash_register_id`). Перевод без получателя
(старые данные) баланс не меняет. **Операции с `cash_register_id = NULL` в балансы касс не
попадают** — так работают оплаты со счёта и кешбэком.

### Доход на дашборде

Сумма `income`-операций за период — **независимо от кассы**. Поэтому оплата со счёта
признаётся выручкой в момент визита, хотя в кассу денег не пришло.

### Важное следствие (принято заказчиком)

Пополнение и возврат депозита **не создают операций в шарде** и не видны в кассе. Физические
деньги в кассе не совпадут с балансом кассы в CRM на сумму «пополнения − возвраты».
Способ оплаты при пополнении можно добавить позже без изменения модели (раздел 14 спецификации).

## 3. Счета клиента (Master DB)

### Модели — `app/models/master/account.py`

- **`ClientAccount`**: `client_id`, `kind` = `money` (особовий рахунок) / `cashback` (кешбек карты),
  `loyalty_card_id` (у cashback, unique), `balance` — **кэш суммы журнала**.
  - money-счёт: один на клиента (частичный unique-индекс), создаётся лениво при первой операции.
  - cashback-счёт: один на карту, создаётся при выдаче карты.
- **`AccountTransaction`** — журнал, **только INSERT**: `type`, `amount` (со знаком),
  `balance_after`, `salon_id` (где проведено), `record_id` / `receipt_id` (ссылки на шард без FK),
  `staff_*` (сотрудник из формы пополнения — только учёт), `author_*`, `comment`,
  `reverses_id` (unique — сторнировать можно один раз), `idempotency_key` (unique).

Типы операций: `topup` (+), `refund` (−), `payment` (−), `accrual` (+ кешбэк), `reversal` (±),
`adjustment` (±, суперюзер, комментарий обязателен), `burn` (− кешбэк сгорает).

### Единственное место, где меняется баланс — `app/services/ledger.py`

Правила, которые **нельзя нарушать** в новых фичах:

1. Баланс меняется только функцией `ledger.post()` — вместе с INSERT в журнал.
2. Перед этим счёт блокируется: `lock_money_account()` (создаёт счёт через
   `INSERT … ON CONFLICT DO NOTHING`, затем `SELECT … FOR UPDATE`) или `lock_account()`.
3. У каждой операции уникальный ключ идемпотентности; повтор с тем же ключом возвращает уже
   записанную операцию и баланс не трогает. Форматы ключей:
   - `topup:{client}:{Idempotency-Key}`, `refund:…`, `adjustment:…`, `adjustment:card:…`;
   - `pay:{salon}:{receipt}:account` и `pay:{salon}:{receipt}:bonus`;
   - `accrual:{salon}:{receipt}`; `reversal:{txn_id}`; `burn:card:{card}`,
     `burn:ttl:{account}:{date}`.
4. Ошибка исправляется сторно (`ledger.reverse`), а не UPDATE/DELETE.

Код синхронный (`Session`): Celery-воркеры вызывают его напрямую, API — через
`AsyncSession.run_sync(...)`.

Правила счёта: пополнение > 0 (сначала гасит долг — это просто сумма); возврат ≤ положительного
баланса; лимита долга нет (право — у администратора); кешбэк в минус уходит **только** через
сторно уже потраченного начисления, платить кешбэком при балансе ≤ 0 нельзя.

### API — `app/api/admin/accounts.py`

`GET /clients/{id}/account`, `GET …/account/transactions`, `POST …/account/topups`,
`…/refunds`, `…/adjustments`. Ключ идемпотентности — заголовок `Idempotency-Key` (без него —
случайный). Отчёт `GET /finances/client-balances` (суперюзер). В списке клиентов —
`accountBalance`, фильтр `balance=debt|deposit`.

## 4. Расчёт итога — `app/services/checkout.py`

Сервер всегда считает итог сам; клиенту не доверяем.

1. **Продано** = сумма строк. Визит — услуги записи (`record_lines`). Чек без записи —
   **одна строка «товар» на всю сумму** (`sale_lines`; склад не списывается, раздел 15 п. 1).
2. **Бонусные строки** → 0 ₴ (`Line.is_bonus`) и в скидке не участвуют.
3. **Скидка** — одна, наибольшая в гривнах: личная % клиента (`Client.discount_percent`), % уровня
   карты, фиксированная уровня (не больше суммы). При равенстве: личная → % карты → фиксированная.
4. **Итог** = Продано − бонусные − скидка, копейки `ROUND_HALF_UP` (`ledger.money`).

`Context` (`load_context`) собирает из Master: клиента, активную карту, **действующую в этом
салоне** (салон входит в тип карты), уровень, баланс счёта и кешбэка.

Предпросмотр: `GET /records/{id}/checkout[?bonusRecordServiceIds=…]` и
`GET /finances/receipts/checkout?subtotal=&clientId=` (`app/api/admin/checkout.py`). Итог из
предпросмотра клиент присылает при оплате как `expectedTotal` — при расхождении 409.

## 5. Оплата — `app/services/visits.py` + `app/services/payments.py`

Точки входа:
- `POST /records/{id}/payment` → `visits.pay_record` (администратор);
- `POST /finances/receipts` → с `recordId` тот же `pay_record`, без — `visits.sell`
  (продажа; эндпоинт открыт администратору, остальное в `/finances` — суперюзер).

### Порядок записи в две БД (`payments.settle`)

```
шард-транзакция открыта:
  1. receipt_id: из Idempotency-Key (uuid5) или случайный
  2. pg_advisory_xact_lock(receipt_id); чек уже есть → вернуть его (повтор запроса)
  3. запись FOR UPDATE (параллельная оплата той же записи ждёт и получит «уже оплачено»)
  4. проверки, расчёт итога, сумма частей = итог, expectedTotal
Master, отдельная транзакция:
  5. payments.charge(): блокировка money-счёта → payment; кешбек-счёта → payment
     (≤ баланса и лимита % типа карты); списание бонусных услуг. COMMIT Master
шард:
  6. чек, части, операции, снапшоты записи, outbox. COMMIT шарда
  7. ошибка в 6 → откат шарда + reverse_payments() в Master (сторно всего по чеку)
  8. процесс упал между 5 и 6 → ночная сверка сторнирует «висящие» списания
```

**Порядок блокировок в Master везде один:** money-счёт → кешбек-счёт → прогресс бонусов.
Код воркера, которому нужна карта, блокирует карту → кешбек → прогресс и работает отдельной
транзакцией. Новые фичи должны соблюдать этот порядок, иначе появятся дедлоки.

### Операции чека (`visits.create_receipt`)

На каждую часть оплаты — `FinanceOperation(income)` с `cash_register_id = method.cash_register_id`.
У системных способов (`account`, `bonus`) — `NULL`. Обычный способ без кассы — ошибка
«не налаштовано касу». Касса чека — первая касса среди частей, иначе `NULL`.

### Итог 0

Если всё закрыто бонусными услугами или скидкой, части оплаты не нужны — чек на 0 ₴.

### Outbox после оплаты

- `record.updated` (change=paid) — уведомления, как и раньше.
- `loyalty.receipt_paid` — **только если в чеке есть карта**. Payload: чек, запись, клиент,
  карта, Продано, скидка, итог, суммы частей по типам (`account`, `bonus`, `other`), баланс
  счёта **до** оплаты, строки (`kind`, `service_id`, `record_service_id`, `price`, `amount`,
  `is_bonus`).

## 6. Асинхронная часть — `workers/tasks/loyalty.py`

`publish_outbox` (каждые 10 с) отправляет события `loyalty.*` в `loyalty.process_event`
(ретраи с backoff, все шаги идемпотентны).

- **`receipt_paid`** (`loyalty.record_visit`): под блокировкой карты проверяет, что чек в шарде
  жив; пишет факт визита `LoyaltyCardVisit` (unique по салону и чеку), счётчики карты
  (`sold_total`, `paid_total`, `visits_count` — только чеки с записью), начисляет кешбэк,
  двигает прогресс бонусных услуг.
  **Оплачено** = итог − часть кешбэком − часть счёта, ушедшая в минус (по балансу до оплаты).
  База кешбэка — Оплачено, пропорционально строкам включённых типов (услуги / товары).
- **`receipt_cancelled`**: транзакция 1 — сторно списаний со счёта и кешбэка, возврат бонусных
  услуг; транзакция 2 — факт визита `reversed_at`, счётчики −, сторно начисленного кешбэка,
  откат прогресса бонусов.

Отмена чека в шарде (`POST /finances/receipts/{id}/cancel`, суперюзер): чек и операции
`cancelled`, запись снова `unpaid` (снапшот скидки и `is_bonus` сброшены), событие в outbox.
Деньги клиенту возвращаются асинхронно, через секунды.

### Beat

- `burn-expired-cashback` (03:30 UTC): сгорание кешбэка по `cashback_ttl_days`, FIFO; пара
  «операция + её сторно» гасится и не участвует.
- `integrity-check` (04:00 UTC): висячие ссылки; `reconcile_payments` — сторно списаний
  (деньги, кешбэк, бонусные услуги) старше часа, у которых чека в шарде нет или он отменён;
  `resend_missing_visits` — для оплаченных чеков с картой без факта визита сбрасывает
  `published_at` у события, и оно уходит заново.

## 7. Карты лояльности — коротко

`app/models/master/loyalty.py`, `app/services/loyalty.py`, API `app/api/admin/loyalty.py`.

- Тип карты: салоны, кешбэк %, на услуги / товары, лимит оплаты кешбэком (% итога), срок
  сгорания, основа уровней (сумма «Продано» или число визитов), уровни (% и фикс. скидка).
- Карта: одна активная на клиента, номер 16 цифр. Уровень не хранится — считается по счётчикам.
  Удаление — кешбэк сгорает (`burn`), новая карта с нуля.
- Бонусные услуги: правило «каждая N-я услуга бесплатная» с услугами по салонам; прогресс
  `LoyaltyBonusProgress` меняется только вместе с журналом `LoyaltyBonusOperation`
  (`use` — по строке чека, `progress` — по чеку и правилу).

## 9. Сертификаты и абонементы: где встраиваться и что решить

**Ничего из этого не решено** — это ориентиры для анализа и вопросы к заказчику.

### Сертификаты

Что есть: тип способа оплаты `certificate` в enum (обычный, с кассой, без логики).

Вопросы до кода:
- Продажа сертификата — это выручка в момент продажи или обязательство до погашения? Деньги за
  продажу идут в кассу? (У пополнения счёта решили: кассы не трогаем, раздел 2.)
- Сертификат именной или на предъявителя? Общий для сети или салона?
- Частичное погашение и остаток; срок действия и что происходит при истечении.
- Можно ли смешивать с кешбэком, скидкой и счётом в одном чеке; начисляется ли кешбэк на часть,
  оплаченную сертификатом (сейчас «Оплачено» уменьшают только кешбэк и долг).
- Возврат денег за сертификат.

Подходящие механизмы: остаток сертификата хорошо ложится на журнал `ledger` (новый
`AccountKind`, своё списание в `payments.charge` по образцу `_charge_cashback`, ключ
`pay:{salon}:{receipt}:certificate`, сторно при отмене и в сверке). Системный способ оплаты —
по образцу `account` / `bonus` (миграция, `SYSTEM_METHOD_TYPES`). Но старые способы типа
`certificate` с кассой уже могут существовать в салонах — их судьба тоже вопрос (с `bonus`
решили перевести в `other`).

### Абонементы

Что есть: ничего. Ближайший аналог — бонусные услуги: строка записи становится бесплатной
(`Line.is_bonus`, `RecordService.is_bonus`), списание идёт синхронно в Master в той же транзакции,
что и деньги, с журналом и откатом при отмене.

Вопросы до кода:
- Абонемент — N визитов на конкретные услуги, на сумму, на период (безлимит)?
- Общий для сети или салона (у салонов разные каталоги услуг — у бонусных правил это решено
  парами `(salon_id, service_id)`)?
- Продажа абонемента — выручка сразу или по мере визитов? Через кассу?
- Срок действия, заморозка, перенос, возврат неиспользованного.
- Как сочетается с бонусной услугой и скидкой на одной строке (сейчас бонусная строка = 0 ₴ и в
  скидке не участвует); считается ли визит по абонементу в «Продано» / «Візити» карты и
  начисляется ли кешбэк.

### Что обязательно соблюдать

- Деньги и любые «остатки» клиента — только через журнал с блокировкой и уникальным ключом.
- Двойная запись Master → шард — через `payments.settle` (или тот же порядок с компенсацией),
  и новые списания должны попадать в `reverse_payments` и в ночную сверку.
- Асинхронные эффекты — через outbox шарда, идемпотентно.
- Шард-миграции идут по флоту неатомарно — только expand → migrate → contract.

## 11. Подводные камни, на которые уже наступали

- **CI запускает `mypy`** (`backend-deploy.yml`) — гоняйте его локально вместе с `ruff` и `pytest`.
- Два Alembic-окружения: `master` и `shard`. Для autogenerate шарда нужна эталонная БД на head.
- `INSERT … ON CONFLICT` по частичному индексу: предикат — литералом `text("kind = 'money'")`,
  с bound-параметром PostgreSQL индекс не сопоставит.
- `dict(session.execute(...).tuples())` падает (у результата есть `.keys()`) — нужен `.all()`.
- В записи услуги дедуплицируются: одна и та же услуга дважды — одна строка.
