# Лояльність і рахунки клієнтів

Спецификация задачи. Решения согласованы с заказчиком 2026-10-13 по скриншотам старой CRM
(блок «Лояльність» в карточке клиента и окно «Рахунки клієнта»). Кода здесь нет — только постановка.

Делаем одним релизом: особовий рахунок клиента (депозит и долг), карту лояльности с кешбэком,
накопительной и фиксированной скидкой, бонусными услугами, показ баланса в Telegram-боте.

Не входят: сертификаты, абонементы, импорт данных из старой CRM, фискализация (ПРРО),
способ оплаты при пополнении счёта.

---

## 1. Согласованные решения

| # | Решение |
|---|---|
| 1 | У клиента **один денежный счёт** (особовий рахунок) на всю сеть. Плюс — депозит, минус — долг. Типов депозита нет |
| 2 | Счёт общий для сети: пополнил в одном салоне — тратит в любом. У сети один владелец, взаиморасчётов между салонами нет |
| 3 | Пополнение счёта **не затрагивает шард-БД** и кассы: способ оплаты не указывается, деньги в финансах салона не появляются. Поле «Співробітник» — только для учёта |
| 4 | Возврат депозита клиенту разрешён, тоже без кассы. Срока действия у депозита нет. Бонусов за пополнение нет |
| 5 | Счётом можно оплатить всё: услуги и товары, любую часть чека |
| 6 | Недоплата за оказанную услугу записывается долгом: часть чека оплачивается со счёта, баланс уходит в минус. Лимита долга нет, право — у администратора |
| 7 | Завершённый, но не оплаченный визит (`payment_status = unpaid`) долгом **не** считается. Долг появляется только при оплате частью «Особовий рахунок» |
| 8 | Карта лояльности: одна активная на клиента, выдаётся вручную. Номер генерируется системой, можно ввести вручную |
| 9 | Все четыре программы: кешбэк, накопительная % скидка, фиксированная скидка, бонусные услуги. Параметры настраиваются в админке |
| 10 | Кешбэк начисляется от реально оплаченного (без части, оплаченной кешбэком, и без части, ушедшей в долг), на услуги и товары |
| 11 | Лимит оплаты кешбэком и сгорание настраиваются в типе карты. По умолчанию: 100 % чека, не сгорает |
| 12 | Уровни скидки считаются по сумме «Продано» или по числу визитов — выбирается в типе карты |
| 13 | Личная скидка клиента (`discount_percent`) и скидки по карте не суммируются — применяется наибольшая в гривнах |
| 14 | «Продано», «Оплачено», «Візити» считаются с даты выдачи карты |
| 15 | При удалении карты кешбэк сгорает (операцией в журнале) |
| 16 | Бонусная услуга: каждый N-й визит с выбранной услугой бесплатный, N настраивается |
| 17 | Сертификаты и абонементы — отдельная задача |
| 18 | В Telegram-боте клиент видит баланс счёта, номер карты, кешбэк и уровень. Только просмотр, без уведомлений |

## 2. Термины

| Термин | Значение |
|---|---|
| **Особовий рахунок** | Денежный счёт клиента. Баланс > 0 — депозит, < 0 — долг |
| **Кешбек-рахунок** | Бонусный счёт карты лояльности. Не деньги: не возвращается, не уходит в долг |
| **Журнал операций** | Неизменяемый список движений по счёту. Баланс = сумма журнала |
| **Тип карти** | Набор правил карты (например «Мережа Adelante»): кешбэк, уровни скидок, бонусные услуги, салоны |
| **Продано** | Сумма чека до скидок |
| **Оплачено** | Сумма чека после скидок минус часть, оплаченная кешбэком, минус часть, ушедшая в долг |
| **Факт візиту по карті** | Запись в Master DB о каждом оплаченном чеке клиента с картой — из них считаются плитки |

---

## 3. Архитектура

Счета, карты и журнал — в **Master DB** рядом с `Client`: они общие для сети. Чеки, записи и кассы
остаются в шарде салона.

```
                Master DB                              Shard DB салона
  ┌───────────────────────────────────┐      ┌──────────────────────────────┐
  │ client_accounts (money / cashback)│      │ records  (+ скидка, карта)   │
  │ account_transactions  (журнал)    │◄─────│ receipts (+ скидка, карта)   │
  │ loyalty_card_types (+ уровни,     │ sync │ receipt_payments             │
  │   бонусные правила, салоны)       │      │ finance_operations           │
  │ loyalty_cards                     │◄─────│ outbox_events                │
  │ loyalty_card_visits (факты)       │async │                              │
  │ loyalty_bonus_progress            │Celery│                              │
  └───────────────────────────────────┘      └──────────────────────────────┘
```

Правила записи в две БД (продолжение принятого в проекте правила двойных записей):

| Операция | Как пишется | Почему |
|---|---|---|
| Пополнение, возврат, ручная корректировка | Только Master | Решение 3: шард не затрагивается |
| Оплата со счёта или кешбэком | **Синхронно**: сначала Master (под блокировкой счёта), потом шард; при ошибке шарда — компенсирующее сторно в Master | Остаток нужно проверить в момент оплаты |
| Начисление кешбэка, факт визита, счётчики, бонусные услуги | **Асинхронно**: событие в outbox шарда в той же транзакции, что чек → Celery → Master | Не блокирует кассира, повторяется при сбое |
| Отмена чека | Шард (чек отменён + событие в outbox) → Celery → сторно в Master | Порядок «сначала шард» безопасен: деньги вернутся с задержкой в секунды |

Каждая операция в журнале имеет **уникальный ключ идемпотентности** (например
`pay:{salon_id}:{receipt_id}:account`). Повтор запроса или задачи не создаёт вторую операцию.

**Ночная сверка** (к существующей суточной сверке cross-DB): находит операции оплаты в Master, для
которых нет чека в шарде (процесс упал между шагами), и сторнирует их; находит оплаченные чеки с
картой без факта визита и переотправляет событие.

### 4.3. Что меняется в существующем коде

1. **`create_receipt`** (`app/services/visits.py:113`). Сейчас каждая часть оплаты создаёт
   `FinanceOperation(income)` с кассой `method.cash_register_id or cash_register_id` — то есть
   оплата без своей кассы попадает в кассу чека и **завышает её баланс**. Новое правило: для
   способов оплаты без кассы (`account`, `bonus`) операция создаётся с `cash_register_id = NULL`.
   - Доход на дашборде (сумма `income`-операций) остаётся верным — выручка признаётся в момент визита.
   - Баланс касс (`_register_balance`, `list_cash_registers`) считает только операции своей кассы — деньги, которых нет, не появляются.
   - Если в чеке нет ни одного способа с кассой, это больше не ошибка «Для способу оплати не налаштовано касу».
2. **`pay_record`** (`visits.py:198`). Остаётся правило «сумма частей = итог записи», но итог
   пересчитывается сервером с учётом скидки и бонусных услуг (раздел 6). Недоплата закрывается
   частью `account`, а не неполным чеком.
3. **`unpay_record_for_receipt`** (`visits.py:256`) и отмена чека — добавляют событие в outbox для
   сторно в Master.
4. **`POST /finances/receipts`** (продажа товаров без записи, `api/admin/finances.py:689`) —
   те же способы оплаты, скидки и кешбэк, что и при оплате визита.
5. **`Client.card_number`** — заменяется номером карты лояльности. Поиск клиентов по номеру карты
   (`clients.py:140`) ищет по `loyalty_cards.number`. Поле убирается из формы клиента в `web/`;
   колонку удалить отдельной миграцией после переноса значений (если в БД есть реальные номера —
   создать по ним карты).
6. **`Client.discount_percent`** — остаётся, участвует в выборе наибольшей скидки (решение 13).

## 5. Процессы: особовий рахунок

### 5.1. Пополнение (депозит или погашение долга)

Форма как в старой CRM: **Сума** (> 0), **Співробітник** (необязательно), **Коментар**.

1. Создать `money`-счёт, если его нет.
2. Заблокировать счёт, записать `topup`, обновить баланс. Только Master.
3. Если баланс был отрицательным, пополнение сначала гасит долг — отдельной логики не нужно, это
   просто сумма.

Шард и кассы не затрагиваются (решение 3). Журнал счёта сам служит аудитом: кто, где, когда,
сколько, сотрудник, комментарий.

### 5.2. Возврат депозита

Сума ≤ текущий положительный баланс. Записывается `refund`. Кассы не затрагиваются.

### 5.3. Оплата со счёта и запись в долг

Это одна операция — часть чека способом «Особовий рахунок».

- Если баланс ≥ суммы части — тратится депозит.
- Если меньше — баланс уходит в минус, разница становится долгом. Интерфейс явно показывает
  «Буде записано в борг: 300 ₴» и требует подтверждения.

Порядок записи — раздел 6, шаг 4.

### 5.4. Ручная корректировка

Только суперюзер, комментарий обязателен. `adjustment` с любым знаком.

### 5.5. Удаление клиента

Клиент удаляется мягко (`is_active = false`). Если баланс ≠ 0 — предупреждение «У клієнта
депозит / борг N ₴», удаление разрешено, счёт сохраняется.

## 6. Процесс оплаты визита (касса)

### Шаг 1. Предпросмотр

`GET /records/{id}/checkout` возвращает всё для модалки оплаты:

- карта клиента (если активна и действует в этом салоне), текущий уровень;
- кандидаты скидки: личная %, % карты, фиксированная карты — с суммами в ₴ и отметкой, какая выбрана;
- бонусные услуги: какие строки записи можно сделать бесплатными (по `available`);
- итог к оплате;
- баланс особового рахунку;
- кешбэк: баланс и максимум к оплате в этом чеке.

### Шаг 2. Расчёт итога (на сервере, клиенту не доверяем)

1. **Продано** = сумма строк записи (услуги) + товары чека.
2. **Бонусные услуги**: если кассир отметил строку и `available > 0`, строка → 0 ₴, `is_bonus = true`.
3. **Скидка**: от суммы после бонусных строк считаются
   - личная: `discount_percent` клиента × сумма;
   - % карты: `discount_percent` уровня × сумма;
   - фиксированная карты: `discount_fixed` уровня, но не больше суммы.

   Применяется **одна** — наибольшая в гривнах. Источник пишется в `discount_source`.
4. **Итог** = Продано − бонусные строки − скидка. Округление до копеек, `ROUND_HALF_UP`.

### Шаг 3. Проверки оплаты

- Сумма частей = итог (как сейчас).
- Часть `bonus` ≤ баланс кешбэка и ≤ `cashback_max_payment_percent` × итог. Кешбэк в минус не уходит.
- Часть `account` — без ограничения суммы; если уводит баланс в минус, нужно право записи в долг.
- Клиент в записи обязателен для `account`, `bonus`, скидок и бонусных услуг.

### Шаг 4. Запись

1. Сгенерировать `receipt_id` заранее.
2. **Master, одна транзакция**: заблокировать счета → `payment` по `account` и `bonus` (ключи
   `pay:{salon}:{receipt}:account|bonus`) → списать использованные бонусные услуги
   (`available − 1`, `used_total + 1`).
3. **Shard, одна транзакция**: чек со снапшотом скидки и карты, части оплаты, операции (без кассы
   для `account` / `bonus`), запись `paid`, событие `loyalty.receipt_paid` в outbox.
4. Ошибка на шаге 3 → `reversal` всего, что записано на шаге 2, и ошибка пользователю.
5. Падение процесса между шагами 2 и 3 → ночная сверка сторнирует «висящие» операции.

### Шаг 5. Начисления (Celery, событие `loyalty.receipt_paid`)

Payload: салон, чек, запись, клиент, карта, Продано, скидка, части оплаты по типам, баланс счёта до
оплаты, строки (услуга / товар, сумма, `service_id`, `is_bonus`).

1. Если у клиента нет активной карты или карта не действует в салоне — только конец.
2. **Оплачено** = итог − часть `bonus` − часть `account`, ушедшая в минус (вычисляется по балансу до оплаты).
3. **База кешбэка** = Оплачено, распределённое пропорционально по строкам; берутся только строки
   типов, отмеченных в `cashback_on_services` / `cashback_on_products`.
4. Записать факт `loyalty_card_visits` (уникальность по чеку) и обновить счётчики карты.
5. Начислить `accrual` = база × `cashback_percent` (ключ `accrual:{salon}:{receipt}`).
6. Бонусные услуги: для каждого правила, если в чеке есть его услуга (не бонусная), `progress + 1`;
   при `progress = N − 1` → `available + 1`, `accrued_total + 1`, `progress = 0`. То есть N-я услуга
   бесплатная.

Погашение долга позже кешбэк не начисляет.

### Шаг 6. Отмена чека

Шард: чек `cancelled`, запись `unpaid`, событие `loyalty.receipt_cancelled`. Celery в Master:

- `reversal` списаний со счёта и кешбэка — деньги и кешбэк возвращаются;
- `reversal` начисленного кешбэка. Если кешбэк уже потрачен, баланс кешбэка может стать
  отрицательным — это допустимо только через сторно; новые начисления его гасят, платить кешбэком
  при балансе ≤ 0 нельзя;
- факт визита помечается `reversed_at`, счётчики уменьшаются;
- бонусные услуги: использованная возвращается в `available`; начисленная по этому чеку
  откатывается (прогресс −1 или `available − 1`, если ещё не использована, иначе прогресс уходит в
  минус и гасится следующими визитами).

## 7. Процессы: карта лояльности

| Процесс | Правила |
|---|---|
| Выдача | Кнопка «Видати карту» в карточке клиента. Выбор типа, номер — сгенерировать (16 цифр, проверка уникальности) или ввести. Если есть активная карта — нельзя. Создаётся `cashback`-счёт. Счётчики начинаются с нуля (решение 14) |
| Удаление | Статус `deleted`. Кешбэк сгорает операцией `burn`. Бонусные услуги и счётчики остаются на удалённой карте для истории. Новая карта начинается с нуля — **уровень скидки тоже сбрасывается** |
| Фильтр статуса | Селект «Активний / Видалений» в блоке, как в старой CRM |
| Сгорание кешбэка | Если `cashback_ttl_days` задан: Celery beat раз в сутки, FIFO — сгорают начисления старше срока за вычетом уже потраченного |
| Изменение типа карты | Новые проценты и уровни применяются к следующим чекам; уже начисленное не пересчитывается |

Плитки карты:

| Плитка | Источник |
|---|---|
| Кешбек ⓘ | Баланс `cashback`-счёта. В подсказке — % кешбэка и лимит оплаты из типа карты |
| Максимальний % знижки | `discount_percent` текущего уровня |
| Максимальна фіксована знижка | `discount_fixed` текущего уровня |
| Нараховано бонусних послуг | `accrued_total` по всем правилам; рядом «доступно: N» |
| Продано | `sold_total` |
| Оплачено | `paid_total` |
| Візити | `visits_count` |

«Детальніше» раскрывает: тип карты, уровень и сколько осталось до следующего, прогресс бонусных
услуг, историю операций кешбэка и фактов визитов.

## 12. Порядок работ внутри релиза

1. **Движок счетов**: модели Master, журнал, блокировки, идемпотентность; пополнение, возврат,
   корректировка; API счёта.
2. **Финансы шарда**: `account`, системные способы оплаты, nullable касса чека, исправление
   `create_receipt`; оплата со счёта и в долг с компенсацией; сверка.
3. **Карты**: типы карт и салоны, выдача и удаление, факты визитов через outbox, плитки.
4. **Кешбэк**: начисление, оплата, лимит, сторно, сгорание.
5. **Скидки**: уровни, выбор наибольшей, снапшоты в записи и чеке, `/checkout`.
6. **Бонусные услуги**: правила, прогресс, применение и откат.
7. **Web** — параллельно с 2–6 по мере готовности API.
8. **Бот**, обновление документации, удаление `Client.card_number`.

## 13. Обязательные тесты

- Пополнение 800 → оплата визита 500 со счёта → баланс 300; касса салона не изменилась; доход на дашборде +500.
- Визит 1000, наличными 400, со счёта 600 при балансе 0 → долг −600; пополнение 600 → 0.
- Пополнение в салоне A, оплата в салоне B.
- Две параллельные оплаты с одного счёта — обе корректны, баланс сходится с журналом.
- Повтор запроса оплаты с тем же чеком — одна операция.
- Сбой транзакции шарда после списания в Master — сторно, баланс восстановлен.
- Падение между Master и шардом — ночная сверка сторнирует.
- Отмена чека — возврат денег и кешбэка, откат начислений, счётчиков и бонусных услуг.
- Кешбэк: не начисляется на часть, оплаченную кешбэком и ушедшую в долг; лимит % чека; сгорание по сроку.
- Выбор наибольшей скидки из личной, % и фиксированной; бонусная строка не участвует в скидке.
- Каждая N-я услуга бесплатная; использование и откат.
- Удаление карты: кешбэк сгорает, новая карта начинается с нуля.
- Карта не применяется в салоне, которого нет в типе карты.
- Права: майстер не видит кнопок и получает 403; корректировка — только суперюзер.
- Чек, полностью оплаченный со счёта, без кассы.

## 14. Принятые последствия

- **Наличные от пополнения и возврата депозита не отражаются в кассе.** Физические деньги в кассе
  не совпадут с балансом кассы в CRM на сумму пополнений минус возвраты. Выручка при этом верная.
  Способ оплаты при пополнении можно добавить позже без изменения модели: операция `topup` получит
  ссылку на `FinanceOperation` в шарде.
- **Удаление карты обнуляет уровень скидки**, так как счётчики считаются с даты выдачи.
- **Бонусные правила требуют выбирать услуги в каждом салоне**: у салонов разные каталоги услуг.

## 15. Уточнения при реализации (2026-10-13)

| # | Вопрос | Решение |
|---|---|---|
| 1 | У чека нет строк товаров, продажа со склада к чеку не привязана | Чек без записи (`POST /finances/receipts`) — одна строка «товар» на всю сумму. К оплате визита товары не добавляются. Склад не затрагивается |
| 2 | `/finances/*` — только суперюзер, а оплату со счёта проводит администратор | `POST /finances/receipts` открыт администратору; способы оплаты он берёт из существующего `GET /payment-methods` (теперь с системными). Остальное в `/finances` — суперюзеру |
| 3 | В салонах могут быть созданные вручную способы типа `bonus` | Миграция переводит их в `other` (касса и история сохраняются). Системный способ определяется по типу: в салоне ровно один `account` и один `bonus` |
| 4 | Перенос `Client.card_number` | Не переносим. Миграция удаления колонки падает, если в ней есть непустые значения |
| 5 | Скидка в продаже без записи: нет суммы до скидки и предпросмотра | В `POST /finances/receipts` — `subtotal` (Продано) и `expectedTotal`: сервер считает наибольшую скидку, сумма частей = итог. Предпросмотр — `GET /finances/receipts/checkout?clientId=&subtotal=`, ответ как у `/records/{id}/checkout`. Без `subtotal` — как раньше, без скидки |
| 6 | По счётчикам `loyalty_bonus_progress` не восстановить, что списал и начислил конкретный чек | Журнал `loyalty_bonus_operations` (карта, правило, салон, чек, строка записи, вид `use` / `progress`, `reversed_at`), уникален по чеку и правилу (для `use` — по строке). Счётчики меняются только вместе с ним; по нему — сторно при сбое шарда, отмене чека и в ночной сверке |
