## 1. Категории услуг

Сейчас `Service.category` — свободная строка (`"other"` по умолчанию), а `GET /services/categories`
собирает уникальные значения из услуг. Пустую категорию не создать, существующую не переименовать.
Нужно как у склада (`InventoryCategory`).

### Модель

`ServiceCategory` (шард): `id`, `name` (String 128, уникально без учёта регистра), `is_system`,
`created_at`. У `Service` — `category_id` (FK, NOT NULL) вместо `category`.

Системная категория «Інше» (`is_system = true`) — ровно одна на салон: не удаляется, не
переименовывается. Новая услуга без категории попадает в неё.

### Миграция

Каждое уникальное значение `services.category` → категория:

| строка   | название         |
| -------- | ---------------- |
| `hair`   | Волосся          |
| `nails`  | Нігті            |
| `face`   | Обличчя          |
| `body`   | Тіло             |
| `makeup` | Макіяж           |
| `other`  | Інше (системная) |
| другое   | как есть         |

«Інше» создать, даже если услуг с `other` нет.

### API (`/services/categories`, только админ на запись)

- `GET /services/categories` → `[{ id, name, isSystem, servicesCount }]`. Порядок: по алфавиту,
  «Інше» **последней**. `servicesCount` — неархивные услуги. Читать могут все, кто видит услуги
  (форма записи у мастера тоже группирует по категориям).
- `POST /services/categories` `{ name }` → 201 категория. 409 «Категорія з такою назвою вже існує».
- `PATCH /services/categories/{id}` `{ name }` → категория. 409 — как выше; системную — 409
  «Системну категорію не можна змінити».
- `DELETE /services/categories/{id}` → 204. Все услуги категории (включая архивные) переносятся в
  «Інше». Системную — 409.
- Аудит — как у категорий склада.

Формат `GET /services/categories` меняется (был `[{ category, count }]`) — фронт переходит
одновременно, старый формат держать не нужно.

### Изменения в существующих эндпоинтах

- `ServiceOut.category` → `category: { id, name }`.
- `ServiceCreateIn` / `ServicePatchIn`: `categoryId` вместо `category`. Не указан при создании —
  «Інше». Несуществующий id — 422 «Категорію не знайдено».
- `GET /services?category=` → `?categoryId=`.
- `GET /records?serviceCategory=` → `?serviceCategoryId=`.
- Отчёты (`ServiceRowOut`, `CategoryRowOut`): `category: str` → `category: { id, name }`;
  группировка — по id.
- Booking API `GET /api/booking/{slug}/services`: вместо `category` — `category_id`,
  `category_name` (snake_case, как весь Booking API). Сортировка: по названию категории, «Інше»
  последней, внутри — по названию услуги.

## 2. Штрихкод товара

- `Product.barcode`: String(64), nullable. Любая строка до 64 символов; пробелы по краям
  обрезать, пустая строка → `null`.
- Уникален в салоне без учёта регистра (как `sku`), включая неактивные товары. Индекс по
  `lower(barcode)`. Дубликат — 409 «Товар з таким штрихкодом вже існує».
- `ProductCreateIn` / `ProductPatchIn`: `barcode` (в PATCH `null` очищает).
- `ProductOut.barcode` — в полном (админском) представлении.
- `GET /inventory/products?query=` ищет подстроку в `name`, `sku` **и `barcode`** — в том числе по
  последним цифрам штрихкода. Для мастера (списание расходников) поиск по штрихкоду тоже работает.
- Excel-импорт: необязательная колонка «Штрихкод». Дубликат у другого товара — ошибка строки
  в отчёте импорта, строка пропускается. Пустая ячейка у существующего товара штрихкод не стирает.
- Excel-экспорт и шаблон: колонка «Штрихкод» после «Артикул».

## 3. Сортировка склада по марже

Маржа = `(sale_price − cost_price) / sale_price`. Колонку фронт считает сам; сортировка нужна по
всему складу, а не по странице.

- `GET /inventory/products?sort=margin` (`desc` — как у остальных сортировок).
- Товары без одной из цен или с `sale_price = 0` — **в конце** при любом направлении.
- Вторичная сортировка — по названию.

## 4. Конец записи (`endAt`)

Сейчас конец всегда = начало + сумма длительностей услуг. Нужно менять длительность растягиванием
карточки в календаре (за верхний и нижний край, вид «день» и «неделя») и полем «Кінець» в форме.

### `PATCH /records/{id}`

Новое поле `endAt` (LocalDatetime, как `startAt`). Итоговый конец:

| Передано                 | Конец                                                  |
| ------------------------ | ------------------------------------------------------ |
| `endAt`                  | `endAt` (вместе с `startAt`, `serviceIds` или без них) |
| `serviceIds` без `endAt` | новое начало + сумма длительностей услуг (как сейчас)  |
| только `startAt`         | длительность сохраняется (как сейчас)                  |

То есть ручная длительность живёт, пока не меняют состав услуг (или пока не задали новую).

Проверки (422 с понятным текстом):

- конец позже начала — «Кінець запису має бути пізніше за початок»;
- конец в тот же день (Europe/Kyiv), что и начало; ровно 00:00 следующего дня — допустимо;
- шаг не проверять — фронт сам привязывает к сетке (5/15/30/60 мин).

Остальное — как при переносе по `startAt`:

- те же статусы (нельзя для `completed` / `cancelled`);
- мастер — только свои записи (`ensure_own_record` уже есть), админ — любые;
- пересечения не проверяются (админка допускает две записи на одно время);
- проверка відпустки / лікарняного — как сейчас, по дню начала;
- `outsideShift` в ответе считается по новому интервалу;
- цена (`price`, `total_amount`, снапшоты услуг) **не меняется**;
- аудит: `changes["endAt"] = [old, new]`;
- `record.updated` в WebSocket — как сейчас.

Уведомление мастеру в боте: при изменении `startAt` — как сейчас («перенесено»); если изменился
**только конец** — не уведомлять. Напоминание клиенту сбрасывается только при изменении `startAt`
(как сейчас).

### `POST /records`

Необязательное `endAt` с теми же проверками. Не передано — начало + сумма длительностей (как сейчас).
Публичный сайт записи и бот — без изменений: там конец всегда по услугам.
