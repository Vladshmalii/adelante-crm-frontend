## 1. Способы оплаты для администратора

Сейчас `GET /finances/payment-methods` доступен только суперюзеру (весь роутер `/finances` —
`require_superuser`), а оплату визита (`POST /records/{id}/payment`) по ACCESS.md проводит любой
администратор — ему не из чего выбрать способ оплаты.

`GET /payment-methods` (вне `/finances`):

- доступ — администратор и суперюзер; мастеру `403`;
- только активные способы, отсортированные как в «Фінанси → Методи оплат»;
- ответ — `[{id, name}]`, без касс, комиссий и прочих финансовых настроек.

`GET /finances/payment-methods` остаётся как есть.

## 2. Графики работы на период

Сейчас график отдаёт только `GET /staff/{id}/schedule` — шаблон недели и исключения по одному
сотруднику, только администратору. Мастеру свой график недоступен, а фронту пришлось бы
повторять логику `app/services/slots.py` (шаблон + исключения + перерыв).

`GET /schedule?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD&masterId=<uuid>`:

- `dateFrom`, `dateTo` — даты включительно, период не больше 62 дней (`422`);
- `masterId` — необязательный; без него — все активные мастера (не уволенные);
- мастер получает только свой график (`masterId` чужой → `403`, без `masterId` — только он);
- рабочие окна считаются той же логикой, что и слоты (`_MasterCalendar.windows`), с учётом
  исключений и перерыва.

```jsonc
{
  "data": [
    {
      "masterId": "…",
      "days": [
        {
          "date": "2026-09-28",
          "isWorkDay": true,
          // Рабочие интервалы дня по Киеву; перерыв уже вырезан
          "windows": [
            { "start": "09:00", "end": "13:00" },
            { "start": "14:00", "end": "19:00" },
          ],
          // Исключение, если оно действует в этот день; иначе null
          "exception": { "type": "vacation", "comment": "Відпустка" },
        },
      ],
    },
  ],
}
```

## 3. Сводка записей по дням

Вид «Місяць» показывает по дню до трёх мастеров с числом записей и «+N ще», мини-календарь —
кольцо загруженности дня. Грузить ради этого все записи месяца (`GET /records`, `perPage ≤ 500`)
дорого и упирается в лимит.

`GET /records/daily-summary?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD&masterId=<uuid>`:

- `dateFrom`, `dateTo` — даты включительно, не больше 62 дней;
- отменённые записи не считаются;
- мастер — только свои записи (как в `GET /records`), очереди «Без майстра» у него нет;
- `bookedMinutes` — сумма длительностей записей; `workMinutes` — сумма рабочих окон мастеров из
  п. 2 (для записей без мастера — `null`). Загруженность = `bookedMinutes / workMinutes`, считает
  фронт.

```jsonc
{
  "data": [
    {
      "date": "2026-09-28",
      "total": 14,
      "bookedMinutes": 780,
      "workMinutes": 1500,
      "byMaster": [
        { "masterId": "…", "count": 6, "bookedMinutes": 360, "workMinutes": 540 },
        { "masterId": null, "count": 2, "bookedMinutes": 90, "workMinutes": null },
      ],
    },
  ],
}
```

## 4. Напоминание о визите: статус и выключатель

Сейчас клиенту автоматически уходит напоминание в Telegram за 30 минут (`workers/tasks/reminders.py`),
если клиент привязан к боту. В карточке записи нужно показать, дойдёт ли напоминание, ушло ли оно,
и дать отключить его для конкретной записи. Время напоминания не настраивается (решение
2026-09-28); SMS — позже.

Модель `Record` (шард): новое поле `reminder_enabled: bool`, по умолчанию `true` (для существующих
записей — `true`).

| Где                        | Что                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| `RecordOut`                | `reminderEnabled: bool`, `reminderSentAt: datetime \| null`, `clientTelegramLinked: bool` |
| `POST /records`            | Необязательное `reminderEnabled` (по умолчанию `true`)                                    |
| `PATCH /records/{id}`      | `reminderEnabled`; права — как на остальные поля записи (мастер — по своей записи)        |
| `scan_shard` (напоминания) | Записи с `reminder_enabled = false` пропускает                                            |
| `ClientOut`                | `telegramLinked: bool` (`telegram_user_id is not null`) — для карточки клиента            |

Смена `reminderEnabled` пишется в журнал (`reminder_enabled: [старое, новое]`).

## 5. Отмена списания расходника

`POST /records/{id}/consumables` списывает товар движением `write_off`, но ошибочное списание
отменить нельзя — только коригуванням остатка вручную, без связи с записью.

`DELETE /records/{id}/consumables/{movementId}`:

- создаёт обратное движение `receipt` на то же количество с `record_id` записи и причиной
  «Скасування списання: <клієнт>»; исходное движение не удаляется;
- повторная отмена того же списания → `409`; в `GET /records/{id}/consumables` отменённое
  списание не показывается (или помечается `cancelled: true` — на выбор бекенда, описать в ответе);
- права — как у списания: администратор; мастер — по своей записи;
- по завершённой и оплаченной записи — тоже можно (ошибки находят после визита).

## Не нужно (уже есть или решено иначе)

| Что                                           | Как                                                                                                    |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Записи на день / неделю                       | `GET /records?dateFrom&dateTo` (фронт догружает страницы, если записей больше `perPage`)               |
| Свободное время («Знайти вільний час»)        | `GET /masters/{id}/slots`                                                                              |
| История изменений записи                      | `GET /records/{id}` → `history`                                                                        |
| Статистика клиента в карточке записи          | `GET /clients/{id}` → `totalVisits`, `totalSpent`, `lastVisit`                                         |
| Мастер создаёт запись новому для него клиенту | `POST /records` с `newClient` — бекенд находит клиента по телефону (`get_or_create_client`), дубля нет |
| Обновление календаря в реальном времени       | WebSocket `record.created` / `record.updated`                                                          |
| Колонка «Адміністрація» в фильтре             | Не нужна: записи бывают только у мастеров                                                              |
