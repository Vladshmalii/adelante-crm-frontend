# Права доступа по ролям

Решение от 2026-09-23. Дополняет [FEATURES.md](./FEATURES.md).

## Роли

| Роль                                                    | Кто это                                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Майстер** (`master`)                                  | Работает только со своими записями и своими клиентами                        |
| **Адміністратор** (`administrator`)                     | Управляет салоном: всё, кроме финансов и выгрузок данных                     |
| **Суперюзер** (`administrator` + `is_superuser = true`) | Администратор с доступом к финансам, выгрузкам и управлению администраторами |

`is_superuser` — булево поле администратора. Первого суперюзера создаёт CLI `salonctl`; дальше
только суперюзер создаёт администраторов и выдаёт или снимает флаг в форме сотрудника.

Часовой пояс для всех дат и времени — `Europe/Kyiv` (фиксированный, не зависит от браузера).

## Матрица

✅ — доступно, ❌ — нет. «Свои» у мастера — записи, где он мастер, и клиенты, у которых была хотя бы
одна запись к нему.

## Допущения (проверить)

Этого в ответах не было — решил по смыслу, поправьте, если не так.

1. **Зарплаты, комиссии и статистика выручки сотрудников считаются финансами** — видит только суперюзер.
   Свой оклад в профиле видит каждый.
2. **Оплату визита проводит любой администратор**, а не только суперюзер: это работа с записью, а не раздел
   «Фінанси». Сам раздел «Фінанси» (кассы, операции, документы, дашборд) — только суперюзер.
3. **Мастер может отменить свою запись.** Если отмена должна быть только за администратором — убрать строку.
4. **Мастер не видит отзывы о себе.** Раздел «Огляд» ему закрыт целиком.
5. **Импорт клиентов из Excel** доступен любому администратору: запрет касался только выгрузки данных.

## Бекенд

С 2026-09-28 бекенд сам проверяет права (`CurrentUser` / `AdminUser` / `SuperUser` в
`backend/app/api/security.py`): мастеру чужое — `404`, запрещённое действие — `403`. Фронт только
прячет недоступное. `is_superuser` — в токене, в ответе логина и в `GET /auth/me`; администратору
`salary` и `commissionPercent` приходят `null`. WebSocket отдаёт мастеру только события его записей.

Для оплаты визита администратору есть `GET /payment-methods` (только активные способы, без
финансовых настроек); `GET /finances/payment-methods` по-прежнему только суперюзеру. Мастеру
расходники — по своей записи (списание и отмена), выбор товара — только название, единица и
остаток.

## Как это сделано на фронте

- Роль и `isSuperuser` берутся из `GET /auth/me`: `toViewer()` в `shared/auth/access.ts`. Там же
  `canAccess(viewer, section)` — доступ к разделу и `permissions(viewer)` — права на действия;
  в компонентах — хук `useViewer()` → `{ viewer, can }`.
- Закрытый раздел: `beforeLoad` роута вызывает `requireSection` (`routes/-lib/guard.ts`) → страница
  `/forbidden` (403). Пункты меню фильтруются тем же `canAccess`.
- Недоступные кнопки и колонки не рендерим (а не делаем `disabled`), кроме случаев, где важно
  объяснить причину («Суперюзер» у себя в форме — `disabled` с подсказкой; «Завершити візит» без
  мастера — так же).
